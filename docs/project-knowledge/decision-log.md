# 决策记录

## 2026-07-08：采用一个赛事一个工作区

决定将赛事隔离为独立结构化目录，每个赛事目录包含 `competition.json`、`basketball.db`、`photos/`、`exports/` 和 `backups/`。

原因：学校赛事之间数据边界清晰，跨设备复制更直接，也降低导入导出时误混数据的风险。

## 2026-07-08：外部赛事必须先导入再打开

决定不直接打开第三方外部目录，而是通过“导入赛事”复制到软件管理目录后，再从已导入赛事列表打开。

原因：减少路径失效、外部目录被移动、误改原始导出目录等问题。

## 2026-07-08：结构化日志使用 JSON，CSV 仅作报表

决定比赛日志导入导出使用 JSON 结构化文件，CSV 继续作为人工查看报表。

原因：JSON 能完整保留赛事 ID、比赛 ID、事件 ID、名单、事件作废字段、换人关联和快照数据；CSV 不适合作为可靠导入契约。

## 2026-07-08：撤销事件采用审计式作废

决定撤销事件不做物理删除，而是标记作废并记录作废时间、原因和操作人。

原因：学校比赛记录存在赛后复核需求，保留原始事件有利于审计和追责。

## 2026-07-08：场上球员采用状态字段加事件审计

决定用 `MatchRoster.IsOnCourt` 保存当前场上状态，同时用 `Substitution` 事件记录换人审计。

原因：状态字段便于 UI 和重启恢复，事件流水便于赛后复核，两者互补。

## 2026-07-08：暂不做大型 MVVM 重构

决定当前阶段继续沿用 WPF code-behind，实现时只将稳定可复用逻辑抽到服务或投影类。

原因：项目仍在快速补齐核心业务能力，大型架构迁移会增加验证成本。后续当记分台状态流转更复杂时，再优先抽出 `ClockService`、`MatchService` 和 `RosterService`。

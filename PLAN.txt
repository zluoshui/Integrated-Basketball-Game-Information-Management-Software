# 篮球比赛综合信息管理系统开发计划（第三方审查版）

> 角色定位：本文档面向开发者执行，也作为客户、第三方审查者与开发者之间的阶段验收依据。客户为学校单位、非专业技术人员，因此系统优先级不是“功能堆叠”，而是：**简单易用、界面清晰、数据可靠、兼容稳定、便于交付维护**。

---

## 1. 客户总需求重述

### 1.1 球员管理系统

系统应支持学校用户自行建立和维护球员资料库。基础字段至少包含：

- 姓名
- 照片
- 学号
- 队伍 / 班级 / 院系等可管理归属信息
- 备注

同时必须支持用户自定义球员信息字段，例如：

- 身高
- 体重
- 位置
- 年级
- 专业
- 联系方式
- 运动员等级
- 其他学校自定义字段

自定义字段应尽量做到普通用户可理解、可维护，而不是只能由开发者修改代码。

### 1.2 比赛系统：球员个人数据记录

系统应支持比赛前设置交战双方队伍及参赛名单，并在比赛过程中将数据记录到具体球员名下。

比赛过程中至少支持记录：

- 得分：1 分、2 分、3 分
- 犯规
- 申请暂停
- 篮板
- 助攻
- 抢断
- 盖帽
- 失误
- 其他后续可扩展的篮球常见技术统计

所有记录应形成事件流水，系统根据事件流水实时计算比分、球队统计和球员个人技术统计。

### 1.3 赛程与控制系统

系统应支持基础比赛控制：

- 创建比赛
- 选择主队、客队
- 设置每节时长
- 比赛倒计时
- 开始、暂停、继续、重置
- 当前节次显示
- 比分显示
- 犯规 / 暂停等关键信息显示

### 1.4 非功能性要求

客户为学校单位、非专业技术人员，因此必须重点满足：

- 操作简单：老师或学生工作人员无需培训即可基本使用。
- 界面美观：布局清楚，记分台按钮大且直观。
- 逻辑科学：数据从事件记录推导，便于撤销、复盘、导出。
- 系统稳定：不能轻易丢数据，不能因误操作导致不可恢复。
- 兼容可靠：优先保证 Windows 11，兼容 Windows 10 22H2 x64。
- 离线可用：第一版不依赖服务器和网络。
- 易交付：提供明确运行方式、安装包或发布包、数据备份说明。

---

## 2. 技术与交付基线

### 2.1 推荐技术选型

默认技术路线：

- C#
- WPF
- SQLite
- Windows 桌面单机应用
- self-contained x64 发布包

目标框架建议由开发者根据实际 SDK 和部署环境确认。原则如下：

1. 如果客户机器能稳定安装并运行目标 .NET 版本，可继续使用当前目标框架。
2. 如果学校机器环境复杂，应优先选择更稳妥、长期支持、部署资料充分的 .NET LTS 版本。
3. 发布给客户时应优先提供 self-contained 包，减少客户机器缺少运行时导致无法启动的风险。

### 2.2 数据存储要求

正式版建议使用 SQLite，不建议长期使用单一 JSON 文件作为主要业务数据库。

原因：

- SQLite 更适合结构化查询。
- 更容易保证数据一致性。
- 更适合后续导出统计、历史比赛查询、数据迁移。
- 比单 JSON 文件更能承受长期使用和数据增长。

照片文件存储在应用数据目录，数据库只保存相对路径。必须设计备份与恢复方案。

### 2.3 工程质量基线

开发者必须至少提供：

- 可执行构建命令
- 可执行运行命令
- 发布包生成方式
- README 使用说明
- 基础自动化测试或自检入口
- 数据库 schema 版本机制
- 明确的错误提示和数据备份策略

---

## 3. 总体架构建议

建议采用轻量分层，不要求过度工程化，但必须避免所有逻辑堆在一个窗口文件中。

推荐结构：

```text
UI / Views
  负责界面展示和用户交互

ViewModels / Presentation
  负责界面状态、绑定数据、按钮命令

Application Services
  PlayerService
  TeamService
  MatchService
  RosterService
  MatchEventService
  ClockService
  ExportService

Domain / Models
  Player
  Team
  Match
  MatchRoster
  MatchEvent
  PlayerStats
  ScoreProjection

Persistence
  SQLite repositories
  Migration scripts
  Photo storage
  Backup / restore

Tests / Self-check
  统计逻辑测试
  数据存储测试
  核心流程自检
```

第一版不强制完整 MVVM，但开发者至少应将以下逻辑从窗口 code-behind 中拆出：

- 统计计算
- 数据保存和读取
- 比赛事件记录
- 比赛计时状态计算
- 球员增删改查
- 数据导出

---

## 4. 分阶段开发与验收计划

后续每个阶段完成后，第三方审查者将独立测试该阶段，并将问题以专业清单反馈给开发者。开发者不得在未通过上一阶段核心验收前大规模推进下一阶段，以免问题叠加。

---

# 阶段 0：工程基线与可运行性修复

## 目标

确保项目能在开发环境和客户目标环境中稳定构建、运行、发布。该阶段不追求新增业务功能，重点是消除“无法运行、无法交付、无法复现”的基础风险。

## 开发任务

1. 补充或修复项目结构
   - 提供 `.sln` 或明确单项目构建方式。
   - 添加 `.gitignore`，排除 `bin/`、`obj/`、临时文件、IDE 缓存等。
   - 清理不应提交的构建产物。

2. 构建与运行说明
   - 编写 README。
   - 明确 SDK 版本。
   - 明确构建命令。
   - 明确运行命令。
   - 明确发布命令。
   - 明确数据保存位置。

3. 去除硬编码运行路径
   - 启动脚本不得写死类似 `D:\Programs\dotnet\dotnet.exe` 的个人机器路径。
   - 如需保留脚本，应使用环境变量或通用 `dotnet` 命令。

4. 发布策略
   - 生成 Windows x64 self-contained 发布包。
   - 确认在无 SDK 的普通 Windows 机器上可以运行。

5. 自检入口
   - 保留并扩展 `--self-check` 或等价自检命令。
   - 自检至少覆盖统计计算、基础数据读写、事件撤销。

## 阶段验收标准

第三方审查时应能验证：

- 按 README 可完成构建。
- 按 README 可启动应用。
- 发布包可在目标 Windows 环境运行。
- 没有个人绝对路径依赖。
- 关闭应用后再次打开不报错。
- `--self-check` 或自检命令返回成功。

## 不通过条件

出现以下任一情况，阶段 0 不通过：

- 客户机器无法启动程序。
- 构建说明缺失或不可执行。
- 发布包依赖开发者个人路径。
- 数据目录创建失败。
- 程序首次启动即异常退出。

---

# 阶段 1：可靠数据底座与球员资料库

## 目标

建立稳定、可长期使用的球员数据库。该阶段完成后，学校用户应能独立维护球员资料，并确认数据不会轻易丢失。

## 开发任务

1. 数据库落地
   - 使用 SQLite 存储结构化数据。
   - 建立 schema version。
   - 提供迁移机制。
   - 禁止用临时 JSON 作为正式主数据源，除非明确作为导入/导出格式。

2. 球员基础字段
   - 姓名：必填。
   - 学号：建议唯一，可配置是否强制唯一。
   - 照片：支持选择、复制到应用数据目录、显示头像。
   - 队伍 / 班级 / 院系：至少支持一个组织归属字段。
   - 备注。
   - 状态：在队、离队、停用等。

3. 自定义字段
   - 支持新增字段。
   - 支持编辑字段显示名。
   - 支持设置字段类型，至少包括文本、数字、日期、选项或先实现文本并保留扩展接口。
   - 支持字段排序。
   - 支持字段是否必填。
   - 支持为每个球员填写自定义字段值。

4. 查询与列表
   - 支持按姓名、学号、队伍搜索。
   - 球员列表显示关键信息。
   - 点击球员可编辑。
   - 删除球员前必须确认。

5. 数据可靠性
   - 数据库定期或手动备份。
   - 照片丢失时界面应显示占位图，而不是崩溃。
   - 异常读写时给出普通用户能理解的提示。

## 阶段验收标准

第三方审查时应能验证：

- 新增球员后重启仍存在。
- 修改球员后重启仍正确。
- 删除球员有确认提示。
- 上传照片后能显示头像。
- 照片文件被复制到应用数据目录，而不是只引用原路径。
- 新增自定义字段后，多个球员可分别填写不同值。
- 搜索功能能按姓名、学号、队伍过滤。
- 数据库文件和照片目录可被备份。

## 不通过条件

- 照片只显示路径，不显示头像。
- 自定义字段只能写死在代码里。
- 重启后数据丢失。
- 删除无确认。
- 数据读写异常导致程序崩溃。

---

# 阶段 2：队伍、比赛创建与赛前名单管理

## 目标

让用户能在比赛开始前清楚、可靠地设置比赛双方和参赛球员名单。

## 开发任务

1. 队伍管理
   - 支持创建、编辑、停用队伍。
   - 队伍与球员建立明确关系，避免仅依赖自由文本。
   - 队伍名称重复时应提示。

2. 比赛创建
   - 创建比赛名称。
   - 设置比赛日期 / 时间。
   - 选择主队、客队。
   - 设置每节时长。
   - 设置节数，默认 4 节。
   - 可填写比赛地点、备注。

3. 参赛名单
   - 分别为主队、客队选择参赛球员。
   - 支持设置球衣号。
   - 支持设置首发。
   - 防止同一球员重复加入同一场比赛的同一方。
   - 防止同一球员同时出现在主客双方，除非开发者给出明确业务解释并经客户确认。

4. 赛前检查
   - 未选择主客队不能开始比赛。
   - 任一方名单为空不能开始比赛，或必须明确二次确认。
   - 球衣号冲突应提示。

## 阶段验收标准

第三方审查时应能验证：

- 能创建两支队伍。
- 能给队伍添加球员。
- 能创建一场比赛并选择主客队。
- 能分别设置主客队参赛名单。
- 能设置球衣号和首发。
- 重启应用后比赛和名单仍存在。
- 重复加入、球衣号冲突、主客队重复球员有合理提示。

## 不通过条件

- 只能手工输入队伍名称，无法形成稳定队伍数据。
- 比赛名单保存后重启丢失。
- 同一球员可无提示地重复加入。
- 没有赛前校验。

---

# 阶段 3：比赛计时与控制系统

## 目标

建立稳定、直观、适合现场使用的比赛控制台。该阶段重点不是技术统计，而是比赛时钟和基础控制必须可靠。

## 开发任务

1. 计时器
   - 显示当前节次。
   - 显示剩余时间。
   - 支持开始、暂停、继续、重置本节。
   - 支持进入下一节。
   - 支持比赛结束。
   - 计时应基于真实时间差计算，避免 UI 卡顿导致计时漂移。

2. 状态控制
   - 比赛状态至少包括：未开始、进行中、暂停中、节间、已结束。
   - 不同状态下按钮可用性应合理。
   - 例如未开始时不能记录比赛事件，或需要明确提示。

3. 数据保存
   - 计时状态应保存。
   - 程序异常关闭或正常关闭后重开，应能恢复到合理状态。
   - 若比赛关闭时仍在计时，重开时必须有明确策略：自动暂停并提示，或按真实时间补偿；不得产生用户无法理解的结果。

4. 前端体验
   - 记分台界面应适合现场使用。
   - 时间、比分、节次应足够醒目。
   - 按钮中文清晰。
   - 避免过多小控件挤在一行。

## 阶段验收标准

第三方审查时应能验证：

- 开始后倒计时减少。
- 暂停后时间停止。
- 继续后从暂停时间继续。
- 重置本节后回到本节初始时间。
- 下一节后节次变化且时间重置。
- 比赛结束后不能继续随意记录事件，或需要明确二次确认。
- 关闭重开后计时状态符合设计说明。

## 不通过条件

- 计时明显漂移。
- 暂停后仍继续扣时间。
- 节次无法推进。
- 关闭重开导致比赛时间异常。
- 按钮状态混乱，用户无法判断当前比赛状态。

---

# 阶段 4：实时球员个人数据记录与事件流水

## 目标

实现比赛过程中对具体球员的实时数据记录，并保证所有统计都可追溯、可撤销、可复核。

## 开发任务

1. 事件类型
   - 得分：1 分、2 分、3 分。
   - 犯规。
   - 暂停申请。
   - 篮板。
   - 助攻。
   - 抢断。
   - 盖帽。
   - 失误。
   - 保留扩展其他事件类型的机制。

2. 记录方式
   - 必须先选择比赛。
   - 必须选择具体球员。
   - 系统根据名单自动判断该球员属于主队或客队。
   - 不允许给非本场名单球员记录数据。
   - 每条事件记录当前节次、表钟时间、球员、队伍、事件类型、分值、备注、创建时间。

3. 实时统计
   - 比分实时更新。
   - 球员个人统计实时更新。
   - 球队犯规和暂停实时更新。
   - 数据应由事件流水推导，而不是手工维护多个容易不一致的计数字段。

4. 撤销与更正
   - 至少支持撤销上一条事件。
   - 推荐支持事件列表中选择某条事件进行撤销或作废。
   - 撤销后比分和个人统计必须同步回退。
   - 撤销操作本身建议记录审计信息，或至少在日志中可见。

5. 操作效率
   - 主队和客队球员应分区显示。
   - 高频按钮应足够大。
   - 可考虑快捷键，但不作为第一验收必要条件。

## 阶段验收标准

第三方审查时应能验证：

- 给主队球员记 +2，主队比分加 2，该球员得分加 2。
- 给客队球员记 +3，客队比分加 3，该球员得分加 3。
- 记录犯规后个人犯规和球队犯规同步增加。
- 记录暂停申请后该球员暂停申请数和球队暂停数同步增加。
- 记录篮板、助攻、抢断、盖帽、失误后个人统计正确。
- 撤销上一条事件后相关统计恢复。
- 非本场名单球员不能被记录。
- 重启后事件流水和统计仍正确。

## 不通过条件

- 比分与事件流水不一致。
- 撤销后统计不回退。
- 可以给非名单球员记数据。
- 球员归属队伍错误。
- 重启后统计结果变化或丢失。

# 阶段 5：比赛日志、统计报表与导出

## 目标

让学校用户能够赛后查看、核对、保存和分享比赛数据。该阶段决定系统是否真正具备“信息管理”价值。

## 开发任务

1. 比赛日志
   - 按时间倒序或正序查看事件。
   - 支持按队伍、球员、事件类型筛选。
   - 显示节次、表钟、球员、队伍、事件、分值、备注。
   - 支持撤销 / 作废记录的显示。

2. 球员统计表
   - 按主队、客队分组显示。
   - 至少包含：得分、犯规、篮板、助攻、抢断、盖帽、失误、暂停申请。
   - 可按得分或姓名排序。

3. 球队统计
   - 主客队比分。
   - 团队犯规。
   - 暂停次数。
   - 总篮板、总助攻等可由个人统计汇总。

4. 导出
   - 至少支持 CSV 或 Excel 导出。
   - 推荐支持 PDF 比赛报告。
   - 导出内容包括：比赛基础信息、比分、球员技术统计、事件流水。

5. 打印友好
   - 表格标题清楚。
   - 中文字段可读。
   - 文件名包含比赛名和日期。

## 阶段验收标准

第三方审查时应能验证：

- 完成一场模拟比赛后能查看事件流水。
- 统计表与比赛中记录的数据一致。
- 撤销事件不应出现在有效统计中，或必须明确标记。
- 能导出文件。
- 导出文件可在常见办公软件中打开。
- 导出内容能被非技术人员理解。

## 不通过条件

- 只能在界面看，无法导出。
- 导出乱码。
- 导出统计与界面统计不一致。
- 事件日志缺少节次或时间信息。

---

# 阶段 6：界面美化、易用性与学校场景优化

## 目标

把系统从“能用”提升到“学校工作人员愿意用、比赛现场不容易误操作”。

## 开发任务

1. 视觉设计
   - 使用统一字体、间距、颜色。
   - 重要信息突出显示：时间、比分、节次。
   - 主队、客队颜色区分。
   - 按钮大小适合现场快速点击。

2. 交互简化
   - 减少现场操作步骤。
   - 记分台页面应优先显示本场球员，而不是全部球员下拉框。
   - 常用操作不应藏在复杂菜单中。

3. 防误操作
   - 删除、重置、结束比赛等危险操作必须确认。
   - 撤销应显示将撤销哪条事件。
   - 比赛进行中切换比赛应提示。

4. 普通用户提示
   - 错误提示使用中文自然语言。
   - 避免显示原始异常堆栈。
   - 对数据保存失败、照片丢失、数据库损坏等情况给出处理建议。

5. 可访问性与显示适配
   - 支持常见屏幕分辨率。
   - 窗口最小尺寸合理。
   - 不应因窗口缩放导致关键按钮不可见。

## 阶段验收标准

第三方审查时应能验证：

- 非技术人员能按界面完成球员创建、比赛创建、记分、导出流程。
- 记分台关键信息在 1 米外仍基本可辨认。
- 危险操作有确认。
- 错误提示不是技术堆栈。
- 窗口缩放后界面仍可用。

## 不通过条件

- 现场记录需要频繁在大量下拉框中查找球员。
- 关键按钮过小或布局混乱。
- 危险操作无确认。
- 普通用户无法理解错误提示。

---

# 阶段 7：稳定性、兼容性与交付验收

## 目标

在交付客户前进行系统级稳定性验证，确保学校场景中可靠运行。

## 开发任务

1. 兼容性测试
   - Windows 11 当前受支持版本。
   - Windows 10 22H2 x64，如客户确有此环境。
   - 无开发 SDK 的普通用户环境。

2. 稳定性测试
   - 连续运行完整模拟比赛。
   - 大量事件记录。
   - 多次关闭重开。
   - 异常输入。
   - 照片文件丢失。
   - 数据库备份和恢复。

3. 数据安全
   - 数据库备份机制。
   - 数据库损坏时的提示和恢复说明。
   - 防止多实例同时写入，或至少启动时检测并提示。

4. 安装与卸载
   - 明确安装方式。
   - 明确卸载是否保留数据。
   - 明确数据备份位置。

5. 交付材料
   - 用户手册。
   - 管理员说明。
   - 常见问题。
   - 版本号。
   - 更新记录。

## 阶段验收标准

第三方审查时应能验证：

- 在目标 Windows 机器上无需开发环境即可运行。
- 完成至少一场完整模拟比赛不崩溃。
- 记录大量事件后界面仍可接受。
- 关闭重开后数据完整。
- 备份恢复流程可执行。
- 多实例启动有检测或提示。
- 用户手册能指导普通用户完成主要流程。

## 不通过条件

- 客户机器无法运行。
- 完整比赛过程中崩溃或明显卡死。
- 数据丢失。
- 无备份恢复说明。
- 无用户手册。

---

## 5. 阶段间依赖关系

建议开发顺序如下：

```text
阶段 0：工程基线与可运行性
  ↓
阶段 1：数据底座与球员资料库
  ↓
阶段 2：队伍、比赛与赛前名单
  ↓
阶段 3：比赛计时与控制
  ↓
阶段 4：实时个人数据记录
  ↓
阶段 5：日志、统计与导出
  ↓
阶段 6：界面美化与易用性
  ↓
阶段 7：稳定性、兼容性与交付
```

说明：

- 阶段 6 的部分界面优化可以穿插在阶段 1-5 中进行，但最终必须集中验收。
- 阶段 7 不应提前压缩，因为客户最关心的是“能稳定用”，而不是只看演示。
- 每阶段都应有可运行版本，不能长期只提交不可运行的半成品。

---

## 6. 第三方审查沟通规则

每个阶段完成后，开发者应提交以下内容：

1. 本阶段完成说明。
2. 涉及的主要文件或模块。
3. 自测结果。
4. 已知问题。
5. 下一阶段计划。
6. 如有需求变更，必须明确说明对时间、功能、稳定性的影响。

第三方审查者将输出：

1. 通过 / 不通过结论。
2. 必须修复问题。
3. 建议优化问题。
4. 与客户需求的偏差。
5. 是否允许进入下一阶段。

问题等级定义：

- P0：阻塞交付或导致数据丢失、程序无法运行，必须立即修复。
- P1：核心功能不符合需求，必须在本阶段修复。
- P2：明显影响使用体验或稳定性，建议本阶段或下一阶段修复。
- P3：优化建议，不阻塞阶段通过。

---

## 7. 当前已有系统的评估结论与改造方向

当前已有系统已经具备 MVP 雏形：

- 球员管理
- 自定义字段雏形
- 比赛创建
- 赛前名单
- 计时
- 事件记录
- 统计推导
- 比赛日志
- 本地保存

但仍存在以下关键差距：

1. 工程交付不足：缺少完整 README、稳定构建说明和正式发布流程。
2. 数据可靠性不足：当前本地 JSON 方案适合演示，不适合长期正式使用。
3. 架构耦合较强：窗口 code-behind 承担过多业务逻辑。
4. 球队模型不充分：队伍和球员关系仍需结构化。
5. 比赛流程不完整：节次推进、比赛结束、状态控制仍需完善。
6. 现场操作体验不足：记分台需要更适合快速点击和防误操作。
7. 缺少正式测试：现有自检只能作为最低保障。
8. 缺少导出和用户手册：不利于学校实际使用和归档。

因此，本计划不建议开发者直接继续堆功能，而应按阶段先补工程基线和数据底座，再完善比赛流程和界面体验。

---

## 8. 第一版范围边界

为保证第一版能稳定交付，以下功能不纳入第一版强制范围：

- 多用户账号系统
- 联网同步
- 云备份
- 手机端
- Web 管理后台
- 自动识别技术统计
- 专业联赛级复杂规则
- 视频回放联动
- 多场地并发比赛管理

这些功能可作为后续版本规划，但不应影响当前学校单机离线稳定版交付。

---

## 9. 最终交付定义

系统达到以下条件，才可视为第一版正式交付：

1. 普通 Windows 用户无需开发环境即可运行。
2. 学校用户可创建和维护球员资料库。
3. 支持自定义球员字段。
4. 可创建比赛并设置双方名单。
5. 比赛中可实时记录球员个人数据。
6. 比分和个人统计由事件流水正确推导。
7. 支持基本计时控制。
8. 支持赛后日志与统计查看。
9. 支持至少一种常用格式导出。
10. 数据重启后不丢失。
11. 有备份恢复说明。
12. 有用户手册。
13. 通过第三方阶段 0-7 验收。

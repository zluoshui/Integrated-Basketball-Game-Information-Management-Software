# 领域模型与数据契约

## 核心领域对象

- `CompetitionManifest`：赛事 manifest，包含赛事 ID、赛事名称、创建时间、更新时间和格式版本。
- `CompetitionWorkspace`：赛事目录、manifest 路径、数据库路径、照片目录、导出目录和备份目录。
- `Player`：球员资料，包含姓名、学号、照片路径、队伍、备注、状态和时间戳。
- `PlayerFieldDefinition` / `PlayerFieldValue`：用户自定义球员字段定义和值。
- `Team`：队伍资料，包含队名、备注、停用状态和时间戳。
- `Match`：比赛资料，包含比赛 ID、名称、主客队、节次、计时规则、状态、备注和时间戳。
- `MatchRoster`：比赛名单，记录比赛、球员、所属队伍、是否首发、球衣号和是否当前在场。
- `MatchEvent`：比赛事件流水，记录比赛、时间点、队伍、球员、关联球员、事件类型、分值、备注、作废信息和创建时间。

## 事件模型

比赛统计以事件流水为准。常见事件包括：

- 得分：1 分、2 分、3 分。
- 技术统计：犯规、篮板、助攻、抢断、盖帽、失误。
- 暂停申请：归属到具体球员，同时影响球队暂停统计。
- 计时控制：记录节次、启动、暂停、重置等审计信息。
- 名单审计：赛中或赛后名单调整必须留下操作人与备注。
- 换人：`Substitution`，`PlayerId` 表示被换下球员，`RelatedPlayerId` 表示换上球员。

统计投影忽略 `ClockControl`、`RosterAudit` 和 `Substitution`，但这些事件必须保留在日志和结构化导出中。

## 作废与审计

撤销事件不应物理删除。事件通过作废字段保留审计痕迹：

- `IsVoided`
- `VoidedAt`
- `VoidReason`
- `VoidedBy`

统计和比分只计算未作废事件。日志界面和结构化导出需要保留作废事件，方便赛后复核。

## 场上球员与换人

比赛准备阶段设置所有参赛球员和首发球员。比赛未开始时，默认场上球员等于首发球员。

`MatchRoster.IsOnCourt` 表示当前是否在场。比赛开始后新增或修改名单默认作为候补，不直接变成场上球员。换人只允许在暂停状态执行，并追加 `Substitution` 事件。

当前规则不强制每队必须 5 名场上球员，以兼容学校测试场景；但同队场上人数不能超过 5。

## 数据库

SQLite 数据库保存在当前赛事工作区的 `basketball.db`。当前 schema 版本为 v6。

迁移原则：

- 每次结构升级递增 schema 版本。
- 迁移必须在事务中执行。
- 只追加迁移脚本，不直接假设用户数据库已经是最新结构。
- 迁移应尽量保留旧数据，并为新增字段设置安全默认值。

当前关键迁移结果：

- `match_rosters.is_on_court`：迁移默认等于 `is_starter`。
- `match_events.related_player_id`：用于换人事件关联换上球员。

## 结构化比赛日志 JSON

结构化比赛日志用于跨设备导入导出，不用 CSV 做导入源。

文件名约定：

```text
matchlog-<competitionId>-<matchId>-<timestamp>.json
```

顶层必须包含：

- 格式名。
- 格式版本。
- 赛事 ID。
- 导出时间。
- 比赛 ID。
- 比赛对象。
- 相关球队快照。
- 相关球员快照。
- 比赛名单。
- 完整事件流水。

导入规则：

- 只能导入当前已打开赛事。
- `competitionId` 必须等于当前赛事 ID。
- 如果 `match.Id` 已存在，跳过并提示重复。
- 如果比赛不存在，导入比赛、名单、事件，并补入缺失的球队和球员快照。
- 不覆盖已有同 ID 的球队或球员主数据。
- 缺少被事件引用的球员快照时拒绝导入。
